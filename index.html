02
MENTAL MODEL
The architecture that shapes everything you do

Claude Code is not a chat interface with programming knowledge. It's an agentic system that reads codebases, executes commands, modifies files, manages git, connects to external services, and delegates to parallel subagents. It operates in three distinct layers.

The Three Layers

3
Extension Layer
MCP · Hooks · Skills · Plugins
External tools (databases, GitHub, Sentry), deterministic automation that fires regardless of model behavior, domain expertise injected just-in-time, packaged extensions for sharing. Configure once, leveraged forever.
2
Delegation Layer
Subagents — up to 10 parallel
Spawn with clean isolated contexts, do focused work, return only summaries to the main thread. Exploration results don't bloat your conversation. Route to Haiku for cheap analysis, Opus for architecture reasoning.
1
Core Layer
Main Conversation Context
Your primary interaction. Every message, file read, and tool output consumes from a context window — 1M tokens by default on current models (Fable 5, Sonnet 5, Opus 4.8/4.7), 200K on legacy models unless upgraded. When context fills, quality degrades. This layer costs money per token. Use it for orchestration and final decisions only.
The key insight: Most users work entirely in the Core Layer, watching context bloat and costs climb. Power users push exploration and specialized work to the Delegation Layer, keep the Extension Layer configured for their workflow, and use the Core Layer only for orchestration.

Core Interaction Modes

modes
# Interactive REPL (primary mode) cd ~/your-project && claude # Start with initial prompt to focus session claude "explain the auth flow in this codebase" # Non-interactive / print mode (scripting) claude -p "list all TODO comments" cat error.log | claude -p "identify root cause" # JSON output for pipelines claude -p "count lines by file type" --output-format json # Plan mode — shows plan before executing ANY changes claude --plan # or inside session: /plan "refactor the auth module" # Continue last session claude -c # Continue specific session claude -r "session-id"
03
CLAUDE.md
The agent's constitution — read every session, no prompting needed

CLAUDE.md is the single highest-leverage file in your entire Claude Code setup. Claude reads it at the start of every session. It's the difference between an agent that knows your project and one you have to re-explain everything to, every time.

Global
~/.claude/CLAUDE.md
Your personal constitution. Coding style, commit format, PR discipline, review priorities. Follows you to every project.
Project
./CLAUDE.md (root)
Team-shared project context. Commit to git. Build commands, architecture decisions, conventions. The whole team benefits.
Scoped
.claude/rules/*.md
Modular rules loaded only when paths match. Avoids token bloat. Use for module-specific conventions instead of dumping everything in root.
Limit
Keep under 200 lines
Every line in CLAUDE.md costs context on every session. Move details to Skills (loaded just-in-time). Import other files with @filename.

Production CLAUDE.md Template

CLAUDE.md
# Project: marketing-advisor ## Stack AWS Lambda + Strands framework + Python 3.12 MCP-connected marketing APIs. Observability: ADOT/OTEL + EMF + X-Ray. ## Build / Test / Lint build: make build test: pytest tests/ -v lint: ruff check . && mypy . deploy: make deploy ENV=$1 ## Conventions - All LLM calls carry correlation trace ID from API gateway - Lambda: flush OTEL spans before return (ADOT layer pattern) - EMF for business metrics, X-Ray for distributed traces - Plan graph nodes must be idempotent - Never use env vars directly — always SSM parameter store - Conventional commits: feat/fix/chore/refactor(scope): msg ## Architecture rules - No synchronous calls for plan generation (Lambda timeout risk) - Strands agents are stateless; state lives in DynamoDB - Always include correlation_id in error logs ## What NOT to do - Don't commit until I approve - Don't write tests that mock the thing being tested - Don't add dependencies without asking first

Memory Shortcut

Inside a session, prefix your message with # to write directly to CLAUDE.md without generating a response:

in-session memory write
# This writes to CLAUDE.md silently, no response generated: # never use print() for debugging — always use structlog with correlation_id # Run /init in a new project to let Claude generate a CLAUDE.md /init
Common mistake: Dumping every project quirk into a single CLAUDE.md. Fix: split into .claude/rules/*.md with paths: globs so each rule loads only when relevant. Aim for ~60 lines in the root file.

05
PERMISSIONS
Fine-grained allow/deny/ask rules that gate every operation

The permission system is what separates an agent you trust to run autonomously from one you have to babysit. Configure it right and you get maximum autonomy with real guardrails.

Permission Rule Syntax

permission patterns
# Tool-level "Read" # allow all reads "Edit(src/**)" # allow edits only in src/ "Read(.env*)" # in deny: block reading .env files # Bash with command prefix matching "Bash(npm run:*)" # allow any npm run ... command "Bash(git:*)" # allow any git command "Bash(rm -rf:*)" # in deny: block rm -rf # MCP tool access "mcp__github" # allow all github MCP tools "mcp__github__create_pr" # allow specific MCP tool only # defaultMode options "acceptEdits" # auto-approve file edits, ask for bash "bypassPermissions" # fully autonomous (use carefully) "default" # ask for everything not in allow list
Never use "defaultMode": "bypassPermissions" in shared project settings. It disables all permission checks for everyone who pulls the repo. Reserve for personal local settings only.

Recommended Starter Permission Set

safe + productive defaults
"permissions": { "allow": [ "Read", "Glob", "Grep", "Edit(src/**)", "Write(src/**)", "Bash(npm run:*)", "Bash(git:*)", "Bash(pytest:*)", "Bash(make:*)" ], "deny": [ "Read(.env*)", "Read(secrets/**)", "Bash(rm -rf:*)", "Bash(sudo:*)", "Edit(.git/**)" ], "ask": ["WebFetch", "Bash(curl:*)", "Bash(docker:*)"] }

08
HOOKS — DETERMINISTIC
18+ lifecycle events. Use hooks for anything that MUST happen. Prompts are advisory. Hooks are law.
Core principle: CLAUDE.md rules can be ignored by a fast-moving agent. Hooks cannot. They run before or after every tool call regardless of model behavior. If something must always happen — formatting, linting, auditing, blocking — put it in a hook, not a prompt.

Hook Lifecycle

UserPromptSubmit
Fires on every prompt. Inject dynamic context: current git branch, open tickets, recent errors, env state.
INJECT CONTEXT
PreToolUse
Fires before any tool call. Validate, audit-log, or block the operation entirely.
EXIT 2 = BLOCK OPERATION
PostToolUse
Fires after each tool execution. Auto-format written files, run linters, sync state to external systems.
Stop
Fires when the agent finishes responding. Run tests, compile, post notifications, update tickets in Jira.
SubagentStop
Fires when a subagent completes. Aggregate results, trigger next step in a pipeline.
Notification
Fires when Claude wants your attention. Route to Slack, desktop notif, sound alert — never miss a long task completing.

Production Hook Examples

hooks in settings.json
"hooks": { // Auto-format Python files on every write "PostToolUse": [{ "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": "ruff format \"$FILE_PATH\" && ruff check --fix \"$FILE_PATH\"" }] }], // Run tests when agent finishes "Stop": [{ "type": "command", "command": "pytest tests/ -x -q 2>&1 | tail -20" }], // Block rm -rf (exit 2 = block) "PreToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "echo \"$TOOL_INPUT\" | python3 -c \"import sys,json; d=json.load(sys.stdin); sys.exit(2 if 'rm -rf' in d.get('command','') else 0)\"" }] }], // Audit log every bash command "PreToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "{ echo \"$(date) CMD:\"; cat; } >> ~/.claude/audit.log" }] }], // Desktop notification when done (macOS) "Notification": [{ "type": "command", "command": "osascript -e 'display notification \"Task complete\" with title \"Claude Code\"'" }] }
09
MCP SERVERS
Thousands of public servers exist. Connect 5–7 well, not all of them.

MCP (Model Context Protocol) turns Claude Code from a file-editing tool into a genuine environment hub. Connect GitHub, databases, Sentry, Slack, your internal APIs — Claude calls them as native tools.

Correction: Public server counts vary wildly by source (estimates range from ~500 to 9,000+ depending on the registry) and the number itself isn't the useful fact. What matters: past roughly 40–50 visible tools, tool-selection accuracy degrades — the model has more options to weigh and picks wrong more often. The practical ceiling most teams land on is 5–7 connected servers. Disconnect anything used less than weekly.

Adding a Server (CLI, preferred) or JSON

claude mcp add — scopes matter
# --scope user: available globally, across all your projects claude mcp add --scope user github \ -- npx -y @modelcontextprotocol/server-github # --scope local (default): per-user, per-project — good for a # project-specific DB or Sentry instance you don't want everywhere claude mcp add --scope local postgres \ -- npx -y @modelcontextprotocol/server-postgres postgresql://localhost/mydb # --scope project: writes to .mcp.json in repo root, shared via git claude mcp add --scope project github \ --transport http https://api.githubcopilot.com/mcp/ \ -e GITHUB_TOKEN=ghp_your_token # List / inspect / remove claude mcp list claude mcp get github claude mcp remove github # Authenticate a server without opening the interactive /mcp menu claude mcp login github claude mcp logout github

Or Configure Directly in .mcp.json

.mcp.json (project root, committed via --scope project)
{ "mcpServers": { "github": { "type": "http", "url": "https://api.githubcopilot.com/mcp/", "env": { "GITHUB_TOKEN": "ghp_..." } }, "postgres": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-postgres", "postgresql://localhost/mydb"] } } }
Config gotcha: A JSON entry with a url but no type field is now a hard error (Claude Code otherwise assumes stdio and skips the server). Always set "type": "http" explicitly. SSE transport is deprecated — use HTTP servers where the vendor offers them.

Tool Search — lazy loading (reduces context ~95%)

Claude Code doesn't load every tool schema from every connected server upfront anymore. Tool Search discovers tools on demand and only pulls in the schema it actually needs — this is what makes running 5-7 servers practical without drowning the context window in unused tool definitions.

High-Value MCP Servers for Your Stack

GitHub (official)
github MCP
Create PRs, comment on issues, review code, search across repos — all from the CLI. Use the official HTTP endpoint over the community stdio server where possible.
AWS MCP servers
AWS / CloudWatch
Query CloudWatch logs, describe Lambda functions, check CloudFormation stacks. Your debugger agent's best friend.
Sentry MCP
Observability
Fetch recent errors, traces, and alerts. Claude can correlate your code changes with production errors automatically.
postgres / supabase MCP
Database
Query your DB directly. Schema introspection, data debugging, migration verification. Use read-only mode against production.
Keep secrets out of committed files: .mcp.json is committed to the repo when added with --scope project. Reference environment variables in the env block rather than inlining tokens directly. Restart Claude Code after adding a server — config is read at startup only.

SUBAGENTS
Up to 10 parallel agents. Isolated contexts. Context bloat killer.

Subagents are the single biggest productivity multiplier most Claude Code users never configure. They spawn with clean contexts, do focused work, and return only summaries — keeping the main conversation lean and your costs down.

Creating a Custom Subagent

.claude/agents/code-reviewer/AGENT.md
--- name: code-reviewer description: Expert code reviewer. Use PROACTIVELY after code changes. tools: Read, Grep, Glob, Bash model: opus permissionMode: plan --- You are a senior engineer performing code review. Focus on: - Correctness and edge cases - Security (OWASP Top 10, secrets in code) - Missing error handling and N+1 queries - Adherence to conventions in CLAUDE.md - Performance anti-patterns Report findings with severity: CRITICAL / HIGH / MEDIUM / LOW

10b
WORKFLOWS & TEAMS
Dynamic Workflows · Agent Teams · /goal · /loop — shipped May–June 2026
Where this fits: Subagents (section 10) are Claude-orchestrated turn-by-turn — Claude decides what to spawn next, and every result lands back in its context. The features on this page move the plan itself out of the conversation: into a script, a scheduled loop, or a team of peers. Reach for these when subagents alone start to buckle under scale or coordination complexity.

Dynamic Workflows — code-orchestrated agent fleets

Announced June 2, 2026. Claude writes a JavaScript orchestration script on demand, custom-built for your task, and a runtime executes it in the background while your session stays responsive. The script — not the conversation — holds the loop, the branching logic, and the intermediate results. Requires Claude Code v2.1.154+.

Why it exists
Context isolation at scale
Old approach (subagents/teams): every result flows back through the conversation, filling the window fast. A workflow calls subagents and collects results into script variables — only the final synthesis reaches your context.
Scale
Up to 1,000 subagents
16 run concurrently at any moment. Bun's team reportedly used this to port ~750K lines from Zig to Rust in 11 days with a two-reviewer-per-file adversarial model, hitting 99.8% test compatibility.
Determinism
Code owns the order
Runs the same way every time instead of depending on whether the model "feels" done. Workflows journal every agent() call so a run can resume — this is why non-deterministic calls like Date.now() are disallowed inside scripts.
Zero coordination tax
Free routing
The coordination layer isn't another model conversation — it's plain JS — so routing the fleet costs zero extra model tokens beyond the agents themselves.

Triggering a Workflow

three ways to start one
# 1. Include the word "workflow" in your prompt Run a workflow to audit every API endpoint under src/routes for missing auth checks. # 2. Just ask in plain English — Claude offers to use one Migrate the auth module from Express 4 to Express 5 using a workflow. Verify all tests pass at each stage. # 3. Force high-effort auto orchestration for the whole session /effort ultracode # Dismiss a suggested workflow for one prompt (doesn't disable the feature) macOS: Option+W Windows/Linux: Alt+W # Run the built-in research workflow /deep-research What changed in the Node.js permission model between v20 and v22? # Inspect running/past workflows /workflows

The Six Coordination Patterns

PatternShapeUse it for
Classify & actOne agent decides task type, script routes accordinglyTriaging inbound bugs vs features vs noise, support ticket routing
Fan out & synthesizeMany small agents, one clean-context each, results merged at a barrierLarge step counts, or steps that shouldn't cross-contaminate context
Adversarial verificationA second agent reviews the first agent's output against a rubricCountering self-preferential bias — the agent that produced output shouldn't grade it
Generate & filterGenerate N ideas, filter/dedupe by rubric, keep only the bestBrainstorming, candidate solution generation, idea ranking
TournamentN agents attempt the same task differently; judge agent picks winner pairwiseHigh-stakes plans worth drafting from several independent angles
Loop until doneRepeats a stage until a condition or budget is metIterative refinement, verification passes, monitoring

Workflow Script Anatomy

.claude/workflows/example.js (structure)
export const meta = { name: 'security-audit', description: 'Audit every route for missing auth checks', whenToUse: 'Run when auditing endpoint security across the repo', phases: [ { title: 'Discover', detail: 'one agent enumerates all route files' }, { title: 'Audit', detail: 'fan out — one agent per route file' }, { title: 'Verify', detail: 'adversarial pass on flagged routes' }, { title: 'Report', detail: 'synthesize findings into one report' }, ], } // budget exposes the token target; null if launched without one // pipeline() by default; parallel() only when a stage needs ALL prior results at once // Date.now(), Math.random(), argless `new Date()` all throw — pass timestamps via args
Cost warning: A workflow spawns many agents, so a single run can use meaningfully more tokens than the same task in conversation. When a run schedules more than 25 agents or its projected token total passes 1.5M, the task panel shows a Large workflow warning. Test on a small slice first — one directory instead of the whole repo — before committing to a full run. You can cap spend by prompting a budget directly: "use 10k tokens".
When it's overkill: Skip workflows for anything under ~10 minutes of work, specs that aren't finalized yet, subjective judgment calls with no clear right answer, or low-stakes tasks where failure costs nothing. Vague prompts like "improve the app" cause subagents to fail to converge and waste tokens — define scope, output format, validation rules, and editing policy explicitly.

Agent Teams — peers, not subordinates

The key difference from subagents: subagents report up to the main session and can't talk to each other. Teammates in Agent Teams communicate directly, share a task list, and challenge each other's findings. Still experimental — disabled by default.

enable agent teams
# settings.json "env": { "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1" } # or shell env var export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 # Then describe the task and teammates in plain English: I'm designing a rate limiter for our API gateway. Spawn three teammates to explore this from different angles: one on UX implications, one on technical architecture, one playing devil's advocate on failure modes. # Claude populates a shared task list, spawns teammates, and # synthesizes findings when they finish. Interact with any # teammate directly from the agent panel below the prompt.
ChooseWhen
SubagentsQuick, focused workers that report back to you. Sequential tasks, same-file edits, work with many dependencies.
Agent TeamsTeammates need to share findings, challenge each other, and self-coordinate. Research/review or cross-layer work (frontend + backend + tests owned separately).
Dynamic WorkflowsThe task needs more agents than one conversation can coordinate, or you want the orchestration codified as a rerunnable script.
Cost note: Agent Teams add coordination overhead and use significantly more tokens than a single session. They work best when teammates can genuinely operate independently — if they constantly need to read each other's output or touch shared files, the coordination messages eat into the very context you were trying to save.

/goal — autonomous multi-hour objectives

Shipped May 12, 2026 alongside Agent View and claude --bg. /goal hands Claude a high-level objective and lets it work toward it autonomously — often for hours — without approving every action. It checks in at decision points rather than barreling through wrong assumptions; total silence through a multi-hour task is a red flag, not the intended behavior.

writing a good /goal prompt
# Bad — no measurable endpoint, over-specifies nothing, under-specifies scope /goal Improve performance # Good — specific outcome, scoped module, testable success condition, explicit constraint /goal Reduce p95 response time on the /api/search endpoint by optimizing the database query in SearchService. Success: p95 under 200ms on the existing load test. Do not touch the auth middleware or change the public API contract.
Good fit
Clear success criteria
"All tests pass" or "the migration is complete" — testable outcomes Claude can verify itself against.
Good fit
Multi-step, sequential work
Step 4 depends on step 3's output. You don't want to manage that sequencing turn by turn yourself.
Poor fit
Unbounded scope
"Improve the app" has no stopping condition. Autonomous agents will touch whatever seems relevant unless explicitly constrained.
Poor fit
Unfamiliar or critical-path code
Hours of unsupervised access is lower-risk on a well-understood module than on something unfamiliar or load-bearing. Commit your working state first.

/loop — scheduled recurring runs

/goal defines when work is done. /loop defines when it should run again. They're complementary, not competing: a workflow can coordinate dozens of agents, a /goal can require agreement across sources before completion, and a /loop can re-trigger the whole thing on a schedule.

loop patterns
# In-session polling on an interval /loop 5m /health-check # Pair a repeatable workflow with a goal and a schedule /loop 1h /deep-research check for new CVEs affecting our dependencies, /goal no unpatched critical CVEs older than 24h

Managed Agents (Platform-level, not local CLI)

These live on the Claude Platform / API, not as local CLI files — but they're the natural next step once your team outgrows local CLAUDE.md + hooks for a production agent. Shipped May 6, 2026.

Research preview
Dreaming
Scheduled process (runs between sessions, not during) that reviews past sessions and memory stores, merges duplicates, resolves contradictions, and surfaces patterns a single agent can't see — recurring mistakes, team-shared preferences. Input store is never modified; review the output before adopting it.
Public beta
Outcomes
Write a rubric describing what "good" looks like. A separate grader — in its own context window, not influenced by the agent's reasoning — evaluates output against it and the agent takes another pass if it falls short. SKILLS & COMMANDS
Reusable prompt templates loaded just-in-time as /slash-commands

Skills are folders with a SKILL.md file in .claude/skills/ (project) or ~/.claude/skills/ (personal). Each skill becomes a /skill-name slash command automatically. They load just-in-time, keeping CLAUDE.md lean.

Naming note: Custom slash commands (the old .claude/commands/*.md files) were merged into Skills as of v2.1.101. Existing .claude/commands/ files still work unchanged, but new work should go in .claude/skills/<name>/SKILL.md. If a skill and a command share the same name, the skill wins.

Skill Frontmatter Options

.claude/skills/deploy/SKILL.md
--- name: deploy description: Deploy the application to an environment argument-hint: "[environment]" user-invocable: true # shows in / menu auto-invocable: false # don't auto-trigger run-in-subagent: true # isolated context disable-model-invocation: false # false = Claude reasons about it --- Deploy the application to the $1 environment (default: staging). Steps: 1. Run the full test suite and abort if any fail 2. Build the production bundle 3. Deploy using ./scripts/deploy.sh $1 4. Verify the health check endpoint returns 200 5. Report deployment status and any anomalies

Powerful Skill Patterns

auto-invocable: true
Auto-triggered skills
Set auto-invocable: true so Claude triggers the skill without being asked. Great for documentation update skills that fire after implementation.
disable-model-invocation: true
Context initializers
Load project state at session start without AI processing. Use for a /load-context skill that injects current sprint tickets, env status, recent deploys.
run-in-subagent: true
Isolated execution
Long-running skills (test suites, deployments, log analysis) run in their own context. Output doesn't bloat your main session.
$ARGUMENTS / $1 $2
Parameterized skills
Pass arguments: /deploy production where $1 = "production". Or use $ARGUMENTS for the full argument string.
Skills vs CLAUDE.md: CLAUDE.md is for always-on context (~60 lines max). Skills are for domain expertise loaded only when needed. Move detailed instructions from CLAUDE.md into skills to slash your per-session context cost.
